# Sequence templates: metre and progressions

**Decision:** Implemented in the canonical Mere and consumer cohorts, 2026-10-16.

The original metre recipe treated each syllable as the next position in a
fixed foot grid. Woodshed progressions establish a second consumer: relative
chord roles can be realized in different keys and arranged into blocks of
different lengths. A word-part contract cannot express those spans faithfully.

## Shared boundary

`scenomise::template` owns integer tick spans, lanes, nested groups, expected
slots, source occurrences, explicit alignment and explained relationships.
The `templated_sequence` recipe compiles these into the existing portable scene
bundle. Ticks are alignment coordinates, not milliseconds or a playback clock.
Groups are bounded to three nesting levels; parents precede children. Unknown
alignment remains unplaced. Missing occupants leave expectations open. A
source can disclose anticipation, sustain, overlap or an alternate realization
without the compiler inventing a failure judgment.

Metre retains its existing input shape and domain reading. It lowers foot
groups and syllable positions to the same sequence geometry used by the generic
recipe, then adds stress heights and rhyme relationships. An observed rhyme
tail and an expected rhyme group retain their distinct meanings.

Woodshed supplies progression roles and song-bar material through an optional
adapter. The initial `SongDoc` convenience adapter supplies explicit ordinal
alignment, one song block per role, bar lengths and beats from `SongDoc`, and
chord resources from the concrete song material. The Set arrangement adapter
below adds independent role spans, persistent card placements and authored rests. The source identity and the occurrence key
remain distinct. No key, cadence, tension, conformity, or performance is
inferred by the shared template compiler.

Graphshell hosts metre and the progression exports with the same chrome,
surface producer, theme, inspection, attention and recipe import/export path.
No application-specific renderer or Woodshed dependency enters Graphshell.

## Alternatives and consequences

Extending `Syllable` to carry chord data would couple layout to one domain.
Adding an unrelated progression renderer would duplicate grouping and
alignment. A full grammar or constraint solver would exceed what either
consumer currently needs. The chosen common structure is deliberately bounded;
metrical scansion and harmonic interpretation remain with their source owners.

The legacy metre JSON still parses; its compiled geometry is regenerated by
the shared layout. Historical receipts remain unchanged. Consumers compiled
against older scene libraries reject the new recipe kind and must update their
cohort. Native panels and audio transport synchronization remain future work. Explicit
Set-to-role alignment is now available through the arrangement adapter below.

## Inputs and reproduction

`progression.json` and `progression-g.json` are actual Woodshed exporter outputs:

```sh
python3 /path/to/mere/support/design-studies/backdrops/with_local_scene_source.py /path/to/mere \
  run -p woodshed-core --features portable-scenes --bin woodshed-progression-scene -- \
  C 'ii-V-I (Jazz)' 100 1,1,2 progression.json
```

Run from Woodshed's checkout. Replace C with G for the second recipe. The
helper can repin that checkout's lockfile; use an isolated checkout. The other
three recipes are copies of the existing illustrative samples for regression
rendering. From Mere:

```sh
cargo run -p pictograph --no-default-features --features backdrop-cpu \
  --example backdrop_receipt -- \
  support/design-studies/backdrops/templates/receipt \
  support/design-studies/backdrops/templates
python3 support/design-studies/backdrops/render_cpu_pngs.py \
  support/design-studies/backdrops/templates/receipt
```

The qualification and source manifest in this directory record the actual
checks and browser environment. CPU paint, browser presentation and native
application integration are separate evidence.

## Canonical integration and explicit Set arrangements

The initial shared API is integrated in Mere `71405bc6d`; Knot, Woodshed and
Signalman received and tested it through their ordinary canonical lockfiles,
without the local cohort helper. Historical receipts above retain their
original source and environment limits. The [follow-up integration receipt](arrangement-receipt/qualification.json)
records the merged-main and canonical receiving checks.

`scenomise::document::SceneDocument` adds a bounded, versioned envelope around
an existing primary recipe and occurrence-linked recipes. Each linked scene is
admitted before replacement; unknown bindings, duplicate bindings, invalid
linked geometry and oversized documents are refused. Bare recipes retain
their existing import/export form. An embedding host selects a linked reading
by occurrence key, lends its own fonts/theme and renders it through the same
portable surface. No domain resolver or source authority enters Graphshell.

Woodshed's explicit Set adapter uses existing persistent `CardId`s and saved
voicing fingerprints. Expected role spans, card placements and authored rests
are independent. Repeated chord resources keep separate occurrence identities,
including after Set reorder, insertion and serialized reopen. Missing
alignment remains unplaced; an unselected voicing remains absent, and an
invalid saved voicing is refused. Capoed shapes retain physical fret and
concert-pitch agreement. The existing SongDoc ordinal convenience adapter
remains available.

`arrangement-regular.json` and `arrangement-varied.json` are actual outputs of
`woodshed-arrangement-scene regular|varied OUTPUT.json`, using the ordinary
`portable-scenes` feature and canonical dependency cohort. Both use the same
ii–V–I expectations. The varied arrangement shortens V, inserts a rest and
splits the tonic across two Cards with different selected voicings. Graphshell
shows these studies alongside metre. Selecting a role or rest does not invent
a related reading; selecting a Card displays its source-supplied fretboard.
The CPU example also renders each document's primary and linked scenes.

These are portable source/model adapters and Graphshell presentation paths.
They do not add native app panels, audio-clock synchronization, new source
editing authority or physical-device qualification.

The [arrangement receipt](arrangement-receipt/qualification.json) records 91
passing source tests across the shared and receiving suites, 14 actual CPU
frames, and the Graphshell WebGPU browser checks. The browser export equals
the source document, successful reimport retains selection, and a document
with an invalid linked scene leaves both displayed views intact. Screenshot,
source and runtime manifests accompany that receipt.
